# 测试状态标记体系 (Test Status Markers)

## 状态一览

E2E-FLOW-PLAN.md 中每个 SP/Flow 步骤的 `状态` 字段，使用以下标记：

### 测试结果标记

| 标记 | 含义 | 颜色 | 说明 |
|------|------|------|------|
| `[x]` | ✅ **测试通过** | 🟢 | 功能完全正常，截图佐证，数据验证一致 |
| `[x][前端正常·无数据]` | ✅ **前端逻辑正确，但无真实数据** | 🟢 | 前端代码没问题，Mock/后端未返回数据（如列表为空），不影响功能判定 |
| `[x][已修复]` | ✅ **修复后通过** | 🟢 | 原来有问题，AI 即时修复代码后重测通过 |
| `[!][前端问题]` | ❌ **前端代码 Bug** | 🔴 | 前端代码逻辑有误（如参数未传、组件绑定错误等），需前端修复 |
| `[!][后端问题]` | ❌ **后端接口 Bug** | 🔴 | 接口返回 404/500/数据格式错误，需后端修复 |
| `[!][Mock问题]` | ⚠️ **Mock 实现不完整** | 🟡 | Mock 拦截器未实现完整逻辑（如搜索不过滤、CRUD 不持久化），前端代码本身没问题 |
| `[!][API参数未传递]` | ❌ **前端代码 Bug — 参数缺失** | 🔴 | api.ts 函数传空 {} 或缺少搜索/分页参数，属于前端代码 bug |
| `[!][分页总数错误]` | ❌ **分页数据不一致** | 🔴 | 分页 total 与列表数据量不匹配 |
| `[!][Mock数据未变更]` | ⚠️ **Mock CRUD 不持久化** | 🟡 | 新增/删除后列表不变，因为 Mock 只返回 success 但未修改内存数据 |
| `[!][搜索无效]` | ❌ **搜索功能失效** | 🔴 | 参数已传但后端/Mock 未按条件过滤 |
| `[!][分页功能无效]` | ❌ **分页功能失效** | 🔴 | 翻页后数据未刷新 |
| `[!][数据问题]` | ⚠️ **测试数据不足** | 🟡 | 表格/下拉为空导致流程走不通，非代码 bug |
| `[!][接口问题]` | ❌ **接口不可用** | 🔴 | 接口 404/500/超时 |
| `[!][元素定位失败]` | ❌ **UI 元素找不到** | 🔴 | snapshot 中找不到目标按钮/输入框 |
| `[!][校验不符预期]` | ❌ **表单校验异常** | 🔴 | 空提交时红字未出现 |
| `[!][路由跳转失败]` | ❌ **路由异常** | 🔴 | 点击后未跳转到预期页面 |
| `[?][待确认]` | ❓ **行为存疑** | 🟡 | 不确定是 bug 还是正常行为，需人工判定 |
| `[SKIP]` | ⏭️ **跳过** | ⚪ | 因前置步骤阻断而跳过 |
| `[ ]` | ⬜ **未执行** | ⬜ | 尚未执行 |

## 修复策略模式 (Fix Strategy) ★★★

测试执行期间发现问题时，有**两种修复策略**，用户启动测试时选择：

### 模式 A：`auto-fix` — 即时修复模式（推荐）

**原则**：阻断性前端问题立即修复 → 重测 → 继续流程。非阻断问题记录后跳过继续。

```
发现问题
  │
  ├─ 是否阻断后续流程？
  │   │
  │   ├─ 是（阻断）
  │   │   │
  │   │   ├─ AI 能修吗？（前端代码问题）
  │   │   │   │
  │   │   │   ├─ 能修 → 【立即修复】→ 重测该 SP
  │   │   │   │   │
  │   │   │   │   ├─ 重测通过 → 标 [x][已修复] → 继续下一个 SP
  │   │   │   │   └─ 重测仍失败 → 标 [!][xxx] → 后续标 [SKIP]
  │   │   │   │
  │   │   │   └─ 不能修（后端问题/需求不明）
  │   │   │       → 标 [!][后端问题] → 后续依赖步骤标 [SKIP] → 跳到下一个不依赖的 Flow
  │   │   │
  │   └─ 否（非阻断）
  │       → 标 [!][xxx] 记录 → 不修，继续下一个 SP
  │
  └─ 所有 SP 执行完毕
      → 生成报告，汇总所有 [!] 问题
```

**auto-fix 修复记录格式**：

```markdown
### SP-001: [index.vue] 列表页搜索
- 状态: [x][已修复]
- 原始问题: [!][API参数未传递] getRehabRecordList() 传空 {}
- 修复内容: 修改 api.ts 添加入参类型，修改 FreeServiceTable.vue 传递搜索参数
- 修改文件:
  - `src/cache/medicalCare/rehabilitation/api.ts` — getRehabRecordList 增加入参
  - `src/views/medicalCare/rehabilitation/components/FreeServiceTable.vue` — 调用时传参
- 重测结果: ✅ 搜索后数据变化，参数正确传递
- 截图: runtime/screenshots/rehabilitation-SP-001-fixed.png
```

### 模式 B：`report-only` — 仅记录模式

**原则**：不修任何代码，只记录问题。阻断的标 [SKIP] 跳过，最后集中输出问题清单。

```
发现问题
  │
  ├─ 是否阻断后续流程？
  │   │
  │   ├─ 是（阻断） → 标 [!][xxx] → 后续依赖步骤标 [SKIP]
  │   │
  │   └─ 否（非阻断） → 标 [!][xxx] → 继续
  │
  └─ 所有可执行 SP 执行完毕
      → 生成报告 + 修复清单（按优先级排序）
```

### 阻断性判定规则

| 问题类型 | 是否阻断 | 理由 |
|---------|---------|------|
| `[!][API参数未传递]` 搜索接口 | **阻断** | 搜索不生效 → 依赖搜索结果的 SP 全部无法验证 |
| `[!][分页总数错误]` | 非阻断 | 分页显示不对但不影响其他功能 |
| `[!][Mock数据未变更]` | 看情况 | 如果后续 SP 依赖新增的数据（如编辑刚新增的记录）→ 阻断 |
| `[!][路由跳转失败]` | **阻断** | 跳不过去后面的页面全测不了 |
| `[!][元素定位失败]` 弹窗触发按钮 | **阻断** | 弹窗打不开里面的表单全测不了 |
| `[!][元素定位失败]` 某个非关键按钮 | 非阻断 | 不影响主流程 |
| `[!][接口问题]` 列表接口 | **阻断** | 列表都加载不出来后面全废 |
| `[!][接口问题]` 导出接口 | 非阻断 | 导出不影响 CRUD 主流程 |
| `[!][校验不符预期]` | 非阻断 | 校验规则有误但提交还是能走通 |
| `[!][后端问题]` | 看情况 | 如果是核心 CRUD 接口 → 阻断，辅助接口 → 非阻断 |

## 状态生命周期 ★★★

每个 SP 的状态会随着测试 → 发现问题 → 修复 → 重测经历一个完整的生命周期：

```
                    ┌──────────────────────────────────────────┐
                    │           SP 状态生命周期                 │
                    └──────────────────────────────────────────┘

[ ] 未执行
 │
 ▼ 执行测试
 │
 ├─ 通过 ────────────────────────────────→ [x] ✅ 测试通过
 │
 ├─ 通过但无数据 ────────────────────────→ [x][前端正常·无数据] ✅
 │
 ├─ 失败（前端问题 + 阻断 + auto-fix 模式）
 │   │
 │   ▼
 │  [!][xxx] 标记问题
 │   │
 │   ▼ AI 立即修复代码
 │   │
 │   ▼ 重测该 SP
 │   │
 │   ├─ 重测通过 ────────────────────────→ [x][已修复] ✅ 修复后通过
 │   │
 │   └─ 重测仍失败 ──────────────────────→ [!][xxx] ❌ 保持失败
 │       │
 │       └─ 后续依赖步骤 ────────────────→ [SKIP] ⏭️
 │
 ├─ 失败（非阻断 或 report-only 模式）
 │   │
 │   ▼
 │  [!][xxx] 标记问题 → 继续下一个 SP
 │
 ├─ 失败（后端问题，AI 无法修复）
 │   │
 │   ▼
 │  [!][后端问题] 标记 → 后续依赖步骤标 [SKIP]
 │
 └─ 行为存疑 ────────────────────────────→ [?][待确认] ❓
     │
     ▼ 用户人工确认
     │
     ├─ 确认是 bug ──────────────────────→ [!][xxx][已确认]
     │
     └─ 确认是正常行为 ──────────────────→ [x] 改为通过
```

## 责任归属速查

### 🔴 前端代码问题（前端必须修复 / auto-fix 可修）

| 标记 | 典型场景 | auto-fix 能力 |
|------|---------|--------------|
| `[!][前端问题]` | 组件绑定错误、事件处理异常 | ✅ 可修 |
| `[!][API参数未传递]` | `getRecordList()` 传空 `{}` | ✅ 可修 |
| `[!][分页总数错误]` | 前端未正确读取 `res.data.total` | ✅ 可修 |
| `[!][元素定位失败]` | 组件条件渲染逻辑有误 | ✅ 可修 |
| `[!][校验不符预期]` | `formRules` 配置有误 | ✅ 可修 |
| `[!][路由跳转失败]` | 路由配置错误 | ✅ 可修 |

### 🔴 后端接口问题（需后端修复，AI 无法修）

| 标记 | 典型场景 | auto-fix 能力 |
|------|---------|--------------|
| `[!][后端问题]` | 接口逻辑错误 | ❌ 不可修 |
| `[!][接口问题]` | 接口 404/500 | ❌ 不可修 |
| `[!][搜索无效]` | （real-api）后端未过滤 | ❌ 不可修 |

### 🟡 Mock 层问题（AI 可修 Mock）

| 标记 | 典型场景 | auto-fix 能力 |
|------|---------|--------------|
| `[!][Mock问题]` | Mock 返回数据结构不对 | ✅ 可修 mock.ts |
| `[!][Mock数据未变更]` | Mock 没实现 CRUD 持久化 | ✅ 可修 mock.ts |
| `[!][数据问题]` | Mock 数据太少 | ✅ 可加 mock 数据 |

### 🟢 无问题

| 标记 | 典型场景 |
|------|---------|
| `[x]` | 完全通过 |
| `[x][前端正常·无数据]` | 前端逻辑对，无匹配数据 |
| `[x][已修复]` | 发现问题 → 即时修复 → 重测通过 |

## 标记使用规则

### 规则 1：一个 SP 只打一个主标记

如果一个 SP 有多个问题，**以根因为准**。

例：搜索后数据不变
- 根因是 api.ts 传空 `{}` → 标 `[!][API参数未传递]`（不标 `[!][搜索无效]`）
- 根因是 Mock 没实现过滤 → 标 `[!][Mock问题]` 或 `[?][待确认]`

### 规则 2：标记后必须附说明文字

```markdown
- 状态: [!][API参数未传递] getRehabRecordList() 传空 {}，搜索条件 elderName/floor/rehabStatus 未传递
```

### 规则 3：`[x][已修复]` 必须附修复记录

```markdown
- 状态: [x][已修复]
- 原始问题: [!][API参数未传递]
- 修复内容: 修改 api.ts + FreeServiceTable.vue
- 修改文件: [api.ts](file:///path/to/api.ts), [FreeServiceTable.vue](file:///path/to/FreeServiceTable.vue)
- 重测结果: ✅
```

### 规则 4：mock 模式 vs real-api 模式的标记差异

| 现象 | mock 模式 | real-api 模式 |
|------|----------|--------------|
| 搜索后数据不变 + 参数没传 | `[!][API参数未传递]` | `[!][API参数未传递]` |
| 搜索后数据不变 + 参数已传 | `[!][Mock问题]` | `[!][搜索无效]` |
| 新增后列表不变 + Mock 无持久化 | `[!][Mock数据未变更]` | N/A |
| 新增后列表不变 + 接口返回成功 | N/A | `[!][后端问题]` |
| 分页 total=0 但有数据 | `[!][分页总数错误]` | `[!][分页总数错误]` |
| 列表为空 | `[x][前端正常·无数据]` | `[!][数据问题]` |

### 规则 5：FLOW-PLAN 头部必须有状态图例和修复策略声明

```markdown
## 测试配置
- 测试模式: mock / real-api
- 修复策略: auto-fix / report-only

## 状态图例
| 标记 | 含义 |
|------|------|
| [x] | ✅ 通过 |
| [x][已修复] | ✅ 即时修复后通过 |
| [x][前端正常·无数据] | ✅ 前端正确，无数据 |
| [!][xxx] | ❌ 失败（详见标签） |
| [?][待确认] | ❓ 待人工判定 |
| [SKIP] | ⏭️ 被阻断跳过 |
| [ ] | ⬜ 未执行 |
```

## 测试报告中的统计维度

| 总 SP 数 | N |

| ✅ 前端正确无数据 [x][前端正常·无数据] | C |

| ❌ 后端问题 | E |
| ⚠️ Mock 问题 | F |
| ❓ 待确认 | G |
| ⏭️ 跳过 | H |

## 修复记录（auto-fix 模式）

| SP | 原始问题 | 修改文件 | 重测结果 |

## 遗留问题清单（需人工处理）

### 🔴 前端问题（优先修复）
