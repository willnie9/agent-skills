# Design Decisions · 架构设计思路与 Trade-off 分析

> 这篇文档记录整套 skill 体系在设计过程中的关键决策。每个决策都标注了"为什么选 A 不选 B"，而不是只告诉你"用了 A"。
>
> 如果你在构建自己的 multi-agent 系统，希望这些 trade-off 分析能帮你少走弯路。

---

## 决策 1：为什么用 Stage Gate 而不是 DAG 编排？

**选项对比**：

| 方案 | 优势 | 劣势 |
|---|---|---|
| **DAG 编排**（LangGraph / Prefect 风格） | 灵活，可任意拓扑，支持并行 | 需要独立的编排引擎，调试复杂，对 skill 体系过重 |
| **Stage Gate 线性流水线** ✅ | 简单、可预测、易调试，每个 gate 就是一个 if-else | 不支持并行 stage，扩展新 stage 需要手动加 gate |

**选择理由**：

前端开发流水线天然是线性的——设计稿解析（A）必须在接口生成（B）之前，B 必须在页面组装（C）之前，C 必须在验收（D）之前。这种场景下 DAG 编排的灵活性是过剩的，反而引入了不必要的复杂度（节点状态管理、边条件表达式、并行冲突处理）。

Stage Gate 的实现也很轻量：`stage-gate.mjs` 只做一件事——读上一阶段的 `stage-report.json`，看 `verdict` 字段是 `pass` / `warn` / `fail`，然后决定继续还是阻断。没有状态机，没有事件总线，一个 50 行的脚本就够了。

**适用边界**：如果你的 agent 系统有 3 个以上的并行分支，或者 stage 之间有复杂的依赖关系（比如 C 依赖 A 和 B 但不依赖 D），DAG 编排会更合适。

## 决策 2：为什么用 Harness Hook 而不是全 Prompt 约束？

**核心认知**：上下文越长 AI 越漂移。

一个 7 skill 协同的流水线，上下文窗口里会堆积几万 token 的历史消息。在这种条件下，靠 prompt 写"别忘了先做粗转再做精修"是扛不住的——AI 不是"忘了"，而是在长上下文中对指令的注意力被稀释了。

**分层策略**：

```
                    ┌─────────────────────────────┐
 高可靠             │  Harness Hook（硬拦截）       │  ← AI 违反 + 级联严重
                    │  PreToolUse / PostToolUse     │     例：enforce-rough-first
                    ├─────────────────────────────┤
 中可靠             │  SKILL.md 铁律（软约束）       │  ← AI 一般能遵守
                    │  模型自觉遵守                  │     例：命名规范、组件选用
                    ├─────────────────────────────┤
 低可靠             │  references/ 参考文档          │  ← 按需加载，不强制
                    │  模型按需查阅                  │     例：代码风格、模板
                    └─────────────────────────────┘
```

**取舍标准**：只有同时满足以下两个条件才上 Harness Hook：

1. AI 天然倾向违反（不是"偶尔犯错"，而是"大概率会跳过"）
2. 违反后失败级联严重（不是"产出略差"，而是"下游全部作废"）

以 `enforce-rough-first` 为例：AI 几乎 100% 会跳过粗转直接精修（因为精修更"有成就感"），而跳过粗转会导致 dom-tree 结构错误，下游的 Vue SFC 生成全部作废——这就是典型的"必须上硬 hook"的场景。

而"命名规范用 kebab-case"这种规则，AI 大多数时候能遵守，偶尔违反了改一下就行，不值得上一个 hook 去拦截每个文件写入操作。

## 决策 3：为什么 Auto 模式要设 4 个必停点？

Auto 模式的关键词是 `auto / yolo / 全跑 / 一气呵成`，触发后跳过所有"等用户确认"的检查点。但我们刻意保留了 4 个即使 auto 模式也必须停下的点：

| 必停点 | 为什么不能跳过 |
|---|---|
| MCP 连接失败 | 没有 MCP 就跑等于盲跑，产出一定不可用 |
| Git 操作 | 不可逆操作，万一覆盖了用户的修改无法挽回 |
| YApi 完全没给（场景 1） | 接口是下游所有 stage 的输入，缺了它后面全是 mock |
| E2E 定位失败（场景 3/4/5） | 增量/迭代/重构模式下找不到目标模块就没法改 |

**设计原则**：auto 模式跳过的是"确认"（你确定要继续吗？），不跳过的是"能力缺失"（你没有条件继续）。区分这两者是 auto 模式安全性的关键。

如果把 auto 模式想象成自动驾驶，确认检查点是"前方有岔路口，向左还是向右？"——auto 模式下默认走规划路线不问。而必停点是"前方道路塌方"——不管什么模式都得停下来。

## 决策 4：为什么用 JSON Schema 做跨 Skill 契约？

**选项对比**：

| 方案 | 优势 | 劣势 |
|---|---|---|
| **自然语言描述** | 灵活，人类友好 | 机器不可校验，AI 容易"自由发挥" |
| **TypeScript interface** | 类型安全，IDE 友好 | 只在编译时校验，跨进程/跨 skill 传 JSON 时失效 |
| **JSON Schema** ✅ | 机器可校验，运行时拦截，与语言无关 | 写起来比 TS interface 啰嗦 |

**选择理由**：

跨 skill 的中间产物是 JSON 文件（`dom-tree.json`、`stage-report.json`），不是 TypeScript 变量。它们在 skill A 的脚本里产出，在 skill B 的 Step 0 里被读取和校验。这个传递过程不经过 TypeScript 编译器，所以 TS interface 无法提供保护。

JSON Schema 配合 `stage-validator.mjs` 可以在运行时做硬校验：字段缺失报错、类型不对报错、枚举值不合法报错。这比"在 SKILL.md 里写清楚 dom-tree 格式然后祈祷 AI 读到了"可靠得多。

**副作用**：JSON Schema 本身也成了文档——新人看 `dom-tree-v1.schema.json` 就能理解 dom-tree 的结构，不需要翻 SKILL.md。

## 决策 5：为什么用 Baseline 做增量执行？

在 auto-ui-explorer 的 E2E 测试场景中，一个模块可能有 50 个页面、200 个交互点。每次改动都全量扫描会浪费大量 token 和时间。

**方案**：`baseline.json` 记录上次完整扫描的快照（页面列表、交互元素、路由路径），下次执行时 `diff-baseline.mjs` 对比差异，只对新增/修改的页面做全量扫描。

**效果**：实测节省 50-70% 的 token 消耗和执行时间。

**代价**：baseline 必须保持更新，否则增量判断会漏。这就是 `enforce-baseline-persist.mjs` 这个 hook 存在的意义——它监控每次 Write/Edit 操作，如果测试产物更新了但 baseline.json 超过 60 秒没同步更新，就发出警告。

这也呼应了决策 2 的思路：AI 大概率会"忘了更新 baseline"，而 baseline 过期会导致增量执行漏测——典型的"必须用机制兜底"的场景。

## 决策 6：为什么 SKILL.md 控制在主流程，详细规范拆 References？

这借鉴了软件工程的"渐进式披露"原则。

SKILL.md 是 AI 执行 skill 时首先加载的入口文件。如果把所有细节都塞进去，会导致两个问题：

1. **上下文膨胀**：SKILL.md 越长，AI 对关键指令的注意力越分散（attention dilution）
2. **加载浪费**：很多 references 只在特定场景下需要（比如"重构模式下的文件冲突处理"），每次都加载是浪费 token

当前结构：

```
SKILL.md（主流程 + 决策树 + 铁律）    ← 每次都加载，控制在合理行数
references/（详细规范、模板、踩坑）     ← 按需加载，SKILL.md 里指明"去读 references/xxx.md"
schemas/（JSON Schema 硬契约）         ← 脚本直接读取，AI 不需要"记住"
scripts/（校验/执行脚本）              ← 脚本执行，不占用上下文
```

**类比**：SKILL.md 相当于函数的签名和注释，references/ 相当于函数内部调用的子模块。你不会把所有实现细节写在函数签名里。

## 决策 7：为什么失败语义分三级而不是两级？

每个 stage 跑完会产 `stage-report.json`，其中 `verdict` 字段有三种值：`pass` / `warn` / `fail`。

为什么不只用 `pass` / `fail` 两级？因为有些 stage 的失败不应该阻断整条流水线：

| Stage | 失败语义 | 理由 |
|---|---|---|
| A（设计稿解析） | fail → 熔断 | 没有 dom-tree，下游全废 |
| B（接口生成） | fail → 熔断 | 没有类型定义，页面组装无法对接 API |
| C（页面组装） | fail → 熔断 | 页面没生成，没什么好验收的 |
| A.recall（token 对比） | warn → 继续 | DSL 有差异但不影响功能，人工复查即可 |
| D（浏览器验收） | warn → 继续 | 验收不通过不意味着代码不能用，可能是环境问题 |

**原则**：主干路径（A → B → C）失败必须熔断，辅助路径（A.recall、D）失败只警告。这让流水线既有严格的质量关卡，又不会因为非关键环节的小问题卡住整个流程。

## 整体架构取舍总结

| 维度 | 我们的选择 | 理由 | 不选的方案 |
|---|---|---|---|
| 编排模式 | Stage Gate 线性流水线 | 前端开发天然是线性依赖 | DAG 编排（过度设计） |
| 约束机制 | Harness Hook + 铁律分层 | 长上下文下 prompt 不可靠 | 全 prompt 约束（太脆弱） |
| 契约格式 | JSON Schema | 机器可校验，跨进程传 JSON | TypeScript interface（只在编译时有效） |
| 自动模式 | auto + 4 个必停点 | 区分"确认"和"能力缺失" | 全自动（太危险）或全手动（太慢） |
| 增量执行 | baseline.json + diff | 节省 50-70% token | 每次全量（太贵） |
| 文档结构 | SKILL.md + references/ | 渐进式披露，减少上下文膨胀 | 全部塞进 SKILL.md（注意力稀释） |
| 失败处理 | 三级语义（pass/warn/fail） | 主干熔断 + 辅助警告 | 两级（pass/fail 太粗暴） |
