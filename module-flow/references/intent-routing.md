# 目标分流与可选前置能力

在选择开发场景前读取本文件。两个新增 skill 保持独立，不相互自动触发；`module-flow` 只在用户要求串联时负责调度。

## 触发优先级

1. 用户明确点名某个 skill 或限定产物，按该范围执行。只要求设计包时，即使同时提供 YApi，也不自动开发。
2. 要求“整理设计并出后端接口方案”，执行设计出包 → 后端分析，完成文档即结束。
3. 要求开发，才进入 A/B/C/A.recall/D。用户要求出设计包、提供外层容器需拆多个场景时，按需先出包；要求后端缺口分析，或业务接口未就绪且要先 Mock 跑通真实业务需求时，先分析后端。纯静态展示不强制做后端分析。
4. 只给链接、无法判断目标时补问一次目标。`auto` 不改变以上优先级。

## 任务字段

`goal` 默认为 `develop`，兼容原开发任务；但自然语言只给链接时不要自行补成开发目标。

| 字段 | 用途 |
|---|---|
| `goal` | `design-package` / `backend-plan` / `design-and-backend-plan` / `develop` |
| `designPackageDir` | 已有设计包路径，或本次出包目标目录；不存在时按设计 skill 的规则创建 |
| `packageImageDir` | 用户提供的截图/切图来源目录；与开发资源输出 `imgDir` 分开 |
| `auditDepth` | 出包的细查深度，默认 2；3 及以上额外导出审计节点 |
| `backendPlanFile` | 已有后端方案路径，或本次方案输出位置 |
| `prepareDesignPackage` | 开发任务是否先出包；独立文档目标由 `goal` 决定 |
| `analyzeBackendGaps` | 开发任务是否先分析后端；独立文档目标由 `goal` 决定 |

文档目标不要求 `module` / `pagePath`。出包需要含来源标识的 MasterGo 外层链接，缺截图时遵循设计 skill 的缺图声明规则。后端方案需要设计包或需求描述，以及可检查的项目代码；不能因链接或代码缺失而编造结果。

## 前置步骤与交付边界

### 设计出包

委托 [mastergo-subdsl-package](../../mastergo-subdsl-package/SKILL.md)，传外层链接、截图来源目录、输出目录和深度。保留真实节点子树、交互原文及来源链接；`audit/` 只作局部检查，不当成业务页面。

交付检查：`manifest.json`、`ai-page-context.md`、来源 DSL 和引用的子 DSL 存在；`selectedLayerId === nodes[0].id`；图片引用有效或显式缺失。现有打包脚本只覆盖其中部分检查，其余依 skill 规则核对，不把脚本退出成功当成全部检查完成。

`goal=design-package` 到此结束。出包完成不自动触发后端分析。

### 后端缺口分析

委托 [backend-gap-mock-plan](../../backend-gap-mock-plan/SKILL.md)，传设计包或需求、当前项目路径和可选方案路径。读取实际接口、类型、页面和代理配置，区分已有能力、提议规格和待确认项。

交付检查：`backend-interface-plan.md`（或指定文件）能按需求逐项追溯来源、代码现状、后端归属、接口/DB/字典/上传变更及待确认项。独立分析不要求浏览器或 YApi，也不自动修改业务代码。

`goal=backend-plan` / `design-and-backend-plan` 到此结束。只有用户已经要求实现时，才继续 Mock 或真实接口开发。

## 衔接现有开发阶段

- 已有设计包先核对来源与本次需求、节点 ID、文件引用；匹配就复用，不默认重新获取或覆盖。用户明确刷新设计时再按设计 skill 重新调用 MCP。
- 后端方案先核对当前源码和需求；有出入则更新相关条目，避免沿用过时字段。
- 从 `manifest.items` 选本次模块对应的主页面及关联弹窗、状态。行为变体通过 `reuseOf` 追溯基础画面，不能把交互节点当作画面。无法判断属于哪个模块时先明确范围，不把整个外层容器当成单个页面。
- Stage A 使用主页面的 `selectedLayerLink` 及关联场景资料执行 `master-go-to-code`。该 skill 当前的拉取脚本仍按链接获取设计数据；本次不提供“设计包直接转换为 dom-tree”的适配器，不把包里的 JSON 冒充代码生成产物。
- Stage A 的临时输出、资源目录与设计包分开，避免清理脚本覆盖设计文档。仍须通过 `validate-dom-tree.mjs`，并保留 A / B / C / A.recall / D 的原有报告和 gate。
- 已有 YApi 时，Stage B 生成实际接口代码。无真实接口的 Mock 开发跳过 Stage B；按方案在 Stage C 生成暂定类型和 Mock，标注待对齐字段，不能把提议接口当成已经上线。
- 真实接口到位后：`yapi-to-code` 获取契约 → 对照后端方案核对字段、路径、结构、枚举 → 更新类型与调用处、替换 Mock → 浏览器验证。仅接口接入无需重新获取设计或重写整个页面。

## 调用示例

- “把这个外层容器整理成设计包，截图在 `./screenshots`，递归到三级”：只运行设计 skill。
- “根据 `./design-package` 和现有设备模块，分析后端缺什么”：只运行后端 skill。
- “先整理这个设计，再出接口方案，先不要写页面”：两个 skill 串联，到文档结束。
- “按这个设计开发设备模块，后端没好，先 Mock”：按需出包 → 后端分析 → A → C → A.recall → D。
- “设计包和接口方案已有，继续开发”：核对并复用文档，执行缺失的实现与验证阶段。
