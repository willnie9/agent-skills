# 后端缺口分析 + Mock-First 交付

## 独立触发与编排

本 skill 可直接读取需求和项目代码，不必先运行 MasterGo 或 `module-flow`。用户只要方案时，交付 Markdown 即结束；只有用户要求实现时才继续开发。`module-flow` 可在“设计出包 → 后端方案”或 Mock 开发前置流程中调用。

## Purpose

把"一个新功能/新需求"落成可执行的后端接口方案，并约定前后端协作节奏：

1. **第一步（通常已由别的 skill 完成）**：设计交付包（MasterGo 用 `mastergo-subdsl-package`），或用户直接给的需求描述。
2. **第二步（本 skill）**：结合项目**现有模块代码**，逐需求分析**后端缺什么**，产出一份整合方案 MD，做到"一个需求一个需求地推进"。
3. **实现节奏**：前期**前端自己写 mock** 跑通页面；后期真实后端接口进来后**批量重构**（不是打补丁）——因为自写 mock 的字段名/接口路径/结构都可能和真实后端不一致。

本 skill 不臆造后端事实：分不清的地方标"待确认"，不硬编字段。

## Required Input

以下任一即可开始：

- 一个设计交付包目录（含 `manifest.json` / `ai-page-context.md` / 交互原文），或
- 一段新需求描述 + 涉及的模块/页面。

## Mandatory Workflow

### 1. 收集改动点，保留原文

从设计包的 `ai-page-context.md`「交互说明/关联交互说明」区块或 `manifest.json` 抽取每个改动点的**交互原文**，逐字保留（不改写、不润色、不猜测）。没有设计包时，把用户需求拆成编号改动点。给每个改动点记下来源图层 ID / 链接（若有）。

### 2. 定位现有模块代码（避免重复造接口）

用 Explore / Grep / Read 找到相关前端代码，重点看：

- 优先读取项目配置和现有目录，确定接口、类型、页面的位置；配置缺失时从源码定位，不能把下列示例路径当作所有项目的固定结构。
- 接口目录（如 `src/cache/**/api.ts`）：现有接口路径与函数签名（**哪些能力已存在**，别重复提"新接口"）。
- 类型目录（如 `src/cache/**/define.ts`）：现有类型/字段/枚举/常量映射。
- 页面目录（如 `src/views/**`）：改动点落在哪个页面/弹窗组件。

列出"现状"再谈"改动"，方案里要能指到具体文件与字段。

### 3. 判定后端归属（关键，别搞错改谁）

分清改动落在**哪个后端**：

- **本仓库后端**：从实际源码确认框架、分层、时间单位、删除策略和数据库约束。例如某项目可能采用 Fastify + `route → controller → service → repository`，但不能默认其他项目也如此。
- **外部服务**：依据请求封装、代理配置和后端路由判断归属。本仓库没有对应实现时，"后端改动"= **提给外部服务团队的接口变更需求**。

判定方法：查 `vite.config.*` 的 proxy、`.env*` 里的 host 变量、以及本仓库 backend 是否有对应路由/表。方案开头必须写明这个前提。

### 4. 逐需求映射到后端方案

每个改动点归类并给出**具体规格**：

- **纯前端**（无后端/接口/DB/字典改动）——明确写"无后端改动"。
- **改字段**（现有接口请求/响应加字段、语义变更）。
- **新接口**（给出 method + path + req/res 结构）。
- **新表 / 加列**（外部服务或本仓库 DB）。
- **字典**（从项目中查明现有查询函数、接口和编码；区分**复用已有码** vs **新增码**）。
- **上传/配置**（从项目中查明上传通道、预签名接口和文件类型限制）。

每条尽量给字段名、类型、单位、必填性、示例 JSON。分不清的进"待确认项"，并写清阻塞了哪一步。

### 5. 产出整合方案 MD

写到设计包目录（如 `<package>/backend-interface-plan.md`），或项目约定位置。结构见 [references/plan-template.md](references/plan-template.md)：

1. **关键前提**（后端归属、字典/上传通道等）。
2. **改动点分类速览表**（每行：需求 | 前端 | 后端接口 | 新接口 | DB | 字典）。
3. **建议实施顺序**（先做地基类需求，如字段/字典扩展）。
4. **逐需求详情**（交互原文要点 → 前端改动 → 后端接口变更 → DB → 字典 → 待确认）。
5. **后端改动汇总清单**（交给后端的一页纸：改字段/改逻辑、新接口、新表、字典、配置）。

方案要能"一个需求一个需求做"，每个需求自成一段、可独立交付。

### 6. Mock-first 实现约定

方案确认后按需求实现前端时：

- 前端先写 **mock**（api 层 `Promise.resolve(...)` 或项目 mock 机制），mock 的字段/路径**视为暂定**，加 `// TODO: 接入真实接口后替换/核对` 标注。
- 遵循项目规范：`interface` 定义类型、禁 `any`、组件/样式规范。
- 不在业务代码里散落硬编码常量替代后端字典（映射常量集中在 `define.ts`）。

### 7. 真实后端到位 → 批量重构（不是打补丁）

真实接口进来后，按**重构**处理：

- 全量核对 mock 与真实接口的**字段名 / 路径 / 请求响应结构 / 枚举值**差异。
- 整体替换 mock，同步更新 `define.ts` 类型与调用处，而不是在旧 mock 上零敲碎打。
- 用户特别强调：自写 mock"字段接口都可能不对"，默认假设有出入，逐条对齐。

## Boundary

- 只做**缺口分析 + 方案 + mock-first 实现约定**；不臆造后端字段，分不清就标"待确认"。
- 不改外部服务代码（只产出接口变更需求）；改本仓库代码时遵循项目分层与规范。
- 与设计类 skill 解耦：`mastergo-subdsl-package` 保持 design-only，本 skill 承接其产物做后端侧分析，但也可脱离 MasterGo 独立使用（任何新需求都适用）。
